== 1. Starting a thread: three ways, same result ==
  main thread is: main
  [c] lambda, running on: worker-c
  [b] Runnable, running on: worker-b
  [a] subclassed Thread, running on: Thread-0
  all three joined; main continues

== 2. start() versus run(): the difference that matters ==
  calling d.run()   ->     ran on: main
  calling d.start() ->     ran on: Thread-1

== 3. Interleaving: the output order is not yours to choose ==
  started 0 1 2 3 4 5, finished in order: 0 3 1 4 2 5
  Thread scheduling is the operating system's decision, not the
  program's. Code that depends on a particular finishing order is
  relying on something nobody guaranteed.

== 4. A race condition, measured ==
  8 threads x 100,000 increments = 800,000 expected

  plain int, counter++                 229,765 /   800,000   lost 570,235  <- UPDATES LOST
  volatile int, counter++              177,394 /   800,000   lost 622,606  <- STILL LOST
  synchronized block                   800,000 /   800,000   lost       0  correct
  AtomicInteger.incrementAndGet        800,000 /   800,000   lost       0  correct

  Why volatile does not help here: `counter++` is three operations --
  read, add one, write back. volatile guarantees each read sees the
  latest value; it does NOT stop another thread from interleaving
  between the read and the write. That gap is the lost update.

== 5. Visibility: the problem volatile actually solves ==
  plain boolean flag : reader exited 2,794 ms after the write  <- NEVER SAW IT (hit the 3s cap)
  volatile flag      : reader exited 0 ms after the write
  (spins recorded by the plain reader: 323,522,386)

== 6. The correct options are not equally cheap ==
  8 threads x 200,000 increments, contended
  synchronized block            :    65 ms  (result 1,600,000)
  AtomicInteger                 :    43 ms  (result 1,600,000)

  Both are correct. AtomicInteger is a single compare-and-swap on one
  variable; synchronized takes a lock and can protect several fields at
  once. Pick by what needs to be atomic TOGETHER, not by the timing --
  a lock protecting two related fields is not replaceable by two atomics.
