Demo B: greedy vs. reluctant vs. possessive quantifiers
Greedy   <.+>   on "<a><b><c>" -> "<a><b><c>" (consumes as much as possible, then backtracks to match)
Reluctant <.+?> on "<a><b><c>" -> "<a>" (consumes as little as possible, expands only on failure)
Possessive <.++> on "<a><b><c>" -> matched: false (never backtracks -- '.' consumes the trailing '>' too, then can't give it back)

Demo C: precompiled Pattern vs. String.matches() (which compiles every call)
200,000 calls to String.matches(): 112 ms (recompiles the pattern every time)
200,000 calls to a precompiled Pattern.matcher(): 21 ms
Speedup: 5.3x

# Honest side-note not shown in this transcript, from exploratory probing before settling
# on the pattern above: the textbook nested-group ReDoS shapes usually cited for this topic
# -- "^(a+)+$", "^(a|aa)+$" against a near-miss run of 'a's -- did NOT reproduce catastrophic
# blowup on this JDK even out to 45 repetitions (consistently 0ms). The adjacent-quantifier
# shape used above ("a*" repeated 15 times before a required literal) DOES reproduce real,
# exponential blowup reliably. Both are genuine, measured findings on this exact JDK build --
# see the chapter's Internal Implementation section for the full comparison and why it matters
# for how you reason about regex safety on modern Java specifically, rather than by folklore.
