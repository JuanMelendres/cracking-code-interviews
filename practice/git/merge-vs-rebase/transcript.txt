Key structural facts, true on every run regardless of hash values:
- The conflict happens on BOTH paths -- rebase does not avoid conflicts, it
  just resolves them one replayed commit at a time instead of once at a merge
  point.
- git merge: 5 commits total, 1 merge commit with 2 parents, both original
  branch tips (C3, C4) preserved unchanged in history.
- git rebase: 4 commits total, fully linear, no merge commit -- but C3's
  commit hash changed (585ef61, not the original 656a18e) because it is
  LITERALLY A NEW commit object with a different parent and therefore a
  different hash. This is why rebasing PUBLISHED/shared commits is dangerous:
  anyone who already pulled the old C3 now has a commit that no longer exists
  on the rewritten branch.
