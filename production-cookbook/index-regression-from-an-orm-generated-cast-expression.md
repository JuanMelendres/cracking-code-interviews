# Index Regression From an ORM-Generated CAST Expression

## Context

An order-history endpoint's primary query filters on a `LIKE` prefix combined with a `status` equality check, backed by a plain index on `status`. A routine Hibernate minor-version upgrade ships, with no accompanying schema change.

## Symptoms

p99 latency on the order-history endpoint triples after the Hibernate upgrade. No schema change shipped in the same release.

## Impact

A routine dependency upgrade, with no visible functional change, causes a significant, user-facing latency regression on a hot-path endpoint.

## Initial Hypotheses

- Connection pool exhaustion — checked and ruled out; pool metrics flat.
- A new N+1 query pattern — plausible, considered.
- A changed query shape generated by the upgraded ORM — plausible, considered.

## Evidence

`pg_stat_statements` shows the endpoint's primary query's `mean_exec_time` up roughly 40x. `EXPLAIN ANALYZE` on the logged query text shows a sequential scan where a composite index scan is expected.

## Investigation Timeline

1. **p99 regression noticed** immediately following the Hibernate upgrade, with no schema change in the same release.
2. **Connection-pool hypothesis ruled out** using flat pool metrics.
3. **Query-level regression confirmed** via `pg_stat_statements`, isolating the specific query responsible for the ~40x execution-time increase.
4. **Plan inspected directly** with `EXPLAIN ANALYZE`, finding a sequential scan in place of the expected composite index scan.

## Root Cause

The upgraded Hibernate version changed how it renders a `LIKE` prefix filter combined with a `status` equality: the new generated SQL wraps `status` in a `CAST(status AS text)`, which defeats the existing plain index on `status`, because the index has no entry for the cast expression's output.

## Immediate Mitigation

```sql
CREATE INDEX CONCURRENTLY idx_orders_status_cast ON orders((CAST(status AS text)));
```

An expression index matching the new generated predicate, applied without locking the table.

## Permanent Fix

Pin the ORM's generated-SQL behavior with a regression test asserting the query plan for the endpoint's hot-path queries, so the next dependency bump is caught by a failing test instead of a production p99 alert.

## Alternatives Considered

Pinning the Hibernate version indefinitely to avoid the regression. Rejected as a long-term strategy — it defers rather than fixes the underlying fragility, and eventually blocks legitimate security or bug-fix upgrades.

## Trade-offs

The expression index is a second index to maintain on every write to `status`. Accepted, because the write volume on `orders.status` is low relative to the read volume on this endpoint.

## Prevention

Add `EXPLAIN`-plan assertions to CI for the top five hot-path queries identified by `pg_stat_statements`, so ORM or library upgrades that change generated SQL are caught before production.

## Monitoring and Alerts

- `pg_stat_statements` mean-execution-time regression per normalized query, alerted per-release — the same check that surfaced this incident, cheap to run automatically on every deploy including dependency-only releases with no application code change.
- An `EXPLAIN`-plan regression test in CI (the Permanent Fix above), run against the actual query text an upgraded ORM generates, not just against hand-written SQL, since this incident's entire mechanism was invisible to any check that didn't inspect the framework's actual output.

## Interview Story

This maps to "why did the planner ignore your index" arriving from a dependency upgrade rather than a code change. Present it as a representative scenario unless you have lived through an equivalent incident:

- **Situation:** a hot-path endpoint's p99 tripled immediately after a routine ORM minor-version upgrade with no schema change.
- **Task:** explain a regression with no obvious code-level cause to investigate.
- **Action:** rule out connection-pool exhaustion using existing metrics; isolate the specific regressed query via `pg_stat_statements`; use `EXPLAIN ANALYZE` to find the sequential scan and trace it to a new `CAST` wrapper in the ORM's generated SQL.
- **Result:** added a matching expression index as an immediate fix, and a CI-level plan-regression test to catch the same class of issue on future ORM upgrades.

## Staff-Level Discussion

This incident generalizes a specific, easy-to-miss risk: an ORM's generated SQL is not a fixed contract — it can change silently between versions, including in minor-version, "routine" upgrades that a team might not review with the same scrutiny as a hand-written query change. The three causes of a planner ignoring an index (selectivity, stale statistics, function or cast wrapping) apply identically whether the wrapping was written by a human or generated by a framework, but the detection burden is different: nobody wrote a line of code that touches the `status` column in this release, so ordinary code review would never have caught it. The Staff-level fix — `EXPLAIN`-plan assertions against actual generated SQL — treats the ORM's output as untrusted and verifiable, not assumed stable, which is the correct posture for any dependency a team doesn't control.
