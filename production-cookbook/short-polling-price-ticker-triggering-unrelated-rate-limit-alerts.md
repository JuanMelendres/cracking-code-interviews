# Short-Polling Price Ticker Triggering Unrelated Rate-Limit Alerts

## Context

A live-price ticker feature had been built on short-polling, specifically because it was the simplest thing to implement, without considering its request-volume cost at scale.

## Symptoms

An unrelated service's rate-limiting dashboard showed a sustained, unusually high request rate from a specific client population, triggering an on-call alert for a service the on-call engineer didn't recognize as related to the actual traffic source.

## Impact

An on-call engineer was paged for a service unrelated to the actual traffic source, and platform-wide rate-limiting infrastructure absorbed load generated by a feature never evaluated against real request-volume cost at production scale.

## Initial Hypotheses

- A client-side retry bug or a bot/scraping pattern — this was the first hypothesis pursued.

## Evidence

The traffic was traced to a live-price ticker widget polling every 500ms per active user session, regardless of whether prices had changed.

## Investigation Timeline

1. **Rate-limit alert triggered** for a service the on-call engineer did not recognize as the real traffic source.
2. **Retry-bug and bot-traffic hypotheses pursued first**, on the assumption the volume was anomalous rather than a designed feature.
3. **Traffic source traced** to a live-price ticker widget, revealing per-session polling every 500ms regardless of whether the price had actually changed.
4. **Scale context confirmed**: the polling design had been fine in early testing with a handful of users and became a real capacity problem once the feature saw meaningful adoption.

## Root Cause

The feature had been built with short-polling because it was the simplest thing to implement, without evaluating its real request-volume cost at scale. Each active user session polled every 500ms unconditionally, so total request volume scaled linearly with concurrent users regardless of whether any price had actually changed.

## Immediate Mitigation

Increased the polling interval as a stopgap, trading responsiveness for reduced request volume.

## Permanent Fix

Replaced the polling loop with a real SSE stream, pushing price updates only when they actually changed.

## Alternatives Considered

A WebSocket connection instead of SSE. Not adopted as the primary fix since the feature only needed one-directional server-to-client push (price updates), which SSE serves with less protocol complexity than a full-duplex WebSocket connection would require.

## Trade-offs

SSE requires holding one open connection per active user instead of brief, stateless requests — a real server-side resource shift. This was accepted because it collapsed per-user request volume from roughly 2/second down to near-zero when prices are stable.

## Prevention

Added a review checklist item requiring any new polling-based feature to justify why SSE or WebSocket isn't a better fit before shipping.

## Monitoring and Alerts

- Request-volume-per-active-user tracked as a first-class metric for any polling-based feature, surfacing an unsustainable design before it triggers a downstream rate-limit incident.
- Cross-service alert attribution improved so a rate-limit spike is traceable to its actual originating feature rather than paging an unrelated on-call rotation.

## Interview Story

This maps to a "why is an unrelated service getting rate-limit alerts" question. Present it as a representative scenario unless you have lived through an equivalent incident:

- **Situation:** a rate-limiting dashboard showed sustained high request volume from a client population, paging an on-call engineer for an unrelated service.
- **Task:** find the actual traffic source and why it was generating that volume.
- **Action:** ruled out a client retry bug and bot traffic; traced the load to a live-price ticker polling every 500ms per session regardless of whether prices changed.
- **Result:** replaced the polling loop with an SSE stream that pushes only on real price changes, collapsing request volume from roughly 2/second per user to near-zero when prices are stable.

## Staff-Level Discussion

The trade-off between polling and a held-open connection (SSE/WebSocket) is real and shows up directly in infrastructure cost and alerting noise, not just architectural elegance — a design choice made for implementation simplicity at low scale imposed a real, compounding request-volume cost that only became visible once adoption grew, and by the time it was visible it was showing up as an alert on a completely unrelated service. That cross-service symptom is itself the Staff-level lesson: request volume from one feature can consume shared rate-limiting or capacity budget that other, unrelated services depend on, so a review checklist gate at design time (justify polling vs. push before shipping) is cheaper than discovering the cost after it has already become someone else's incident.
