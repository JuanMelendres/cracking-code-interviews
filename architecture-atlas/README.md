# Architecture Atlas

The Architecture Atlas owns full system-design reference entries per `CLAUDE.md`'s Architecture Atlas Standard: problem statement, constraints, functional/non-functional requirements, capacity assumptions, architecture diagram, data model, APIs, request flow, consistency model, scaling strategy, reliability strategy, security/observability/cost, trade-offs, alternatives, migration path, Staff-level discussion, and interview presentation sequence — each entry referencing detailed canonical `handbook/` chapters rather than restating their explanations.

## A note on scope

This programme's study packs contain 13 real, worked "design exercise" files across Weeks 3–19, each a timed application of [System Design Method and Estimation](../handbook/system-design/system-design-method-and-estimation.md)'s six-phase method (or a domain-specific variant of it) to a concrete problem. All 8 classic system-design-style exercises — full request/response systems with an architecture diagram, data model, and scaling story — are **fully elevated**: `ride-hailing dispatch` (Week 3), `news feed` (Week 4), `payment processing` (Week 5), `authentication service` (Week 7), `notification system` (Week 8), `distributed job scheduler` (Week 9), `distributed cache` (Week 10), `metrics/monitoring system` (Week 11).

The remaining 5 weeks' exercises (Weeks 15–19) are differently shaped — domain-specific design/review exercises (a deployment-infrastructure strategy, two JVM operational playbooks, a security review, a test-strategy design) rather than classic full-system designs — and use an adapted entry template accordingly: no data model, API surface, or consistency-model sections, since none apply to an infrastructure decision, a diagnostics runbook, or a review. **All 5 are now elevated.** This closed the Atlas against its own original scope: all 13 real, worked design exercises across the programme (Weeks 3–19) are represented, 8 under the classic template and 5 under the adapted one.

**A 14th through 17th entry — [Real-Time Chat System](real-time-chat-system.md), [Ticket and Event Booking System](ticket-and-event-booking-system.md), [URL Shortener System](url-shortener-system.md), and [Distributed Key-Value Store](distributed-key-value-store.md) — were added 2026-09-01.** Unlike every entry above, none is elevated from an existing study-pack exercise — none exists for any of these four problems. All four were added as new, original content toward the Master Topic Register's T-813 (Canonical design problems (12-problem set)), built to the identical Architecture Atlas Standard and six-phase method every other classic entry follows.

**T-813 closure accounting.** The register states a 12-problem target but never enumerates which twelve. Counting only the classic full-system-design entries (the 8 elevated ones plus these 4 new ones — excluding the 5 adapted-template infrastructure/review entries below, which are a structurally different exercise) gives exactly 12: Ride-Hailing Dispatch, News Feed, Payment Processing, Authentication Service, Notification System, Distributed Job Scheduler, Real-Time Chat, Ticket and Event Booking, URL Shortener, Distributed Key-Value Store, Distributed Cache, Metrics/Monitoring. That matches T-813's stated count exactly, so this repository treats **T-813 as closed by count** as of the Distributed Key-Value Store entry (2026-09-01). This is closure against the stated target, not a guarantee that these particular twelve are the exact twelve a given interviewer would pick — no enumerated reference list exists to check that against.

## Entries

| Entry | Companion topic | What it's about |
|---|---|---|
| [Ride-Hailing Dispatch System](ride-hailing-dispatch-system.md) | T-801/T-802 (System Design Method and Estimation) | A location-driven matching system: the central design tension is that driver location (high write volume, staleness-tolerant) and ride state (low volume, correctness-critical) need different storage and consistency treatment, split along that line rather than as an afterthought. Elevated from `study-packs/week-03/08-design-exercise-ride-hailing.md`. |
| [News Feed System](news-feed-system.md) | Caching Strategies and Invalidation | A read-heavy fan-out system: the 200:1 read:write ratio justifies precomputing feeds at write time for most users, but a per-author split (fan-out-on-write vs. fan-out-on-read for the celebrity case) is needed to avoid a catastrophic write spike from a power-law-distributed follower count. Elevated from `study-packs/week-04/08-design-exercise-news-feed.md`. |
| [Payment Processing System](payment-processing-system.md) | Idempotency at System Edges / CAP Theorem | A deliberately low-QPS, high-consequence system where correctness — not throughput — is the binding constraint: idempotency is designed into the API contract from the start, and the honest limits of end-to-end "exactly-once" (dependent on the external provider) are stated explicitly rather than claimed as an unqualified guarantee. Elevated from `study-packs/week-05/09-design-exercise-payment-processing.md`. |
| [Authentication Service](authentication-service.md) | OAuth2, OIDC, and JWT | A ~700x asymmetry between token issuance and token validation drives the whole design: validation happens via local JWT signature verification with no call back to the Auth Service, trading instant revocation for elimination of a synchronous, availability-critical dependency at the platform's highest-traffic path. Elevated from `study-packs/week-07/08-design-exercise-authentication-service.md`. |
| [Notification System](notification-system.md) | Kafka Delivery Semantics and Exactly-Once | A fan-out and delivery-guarantee problem, not a storage problem: `userId` partitioning preserves per-user ordering, per-channel topics isolate a degraded provider from the others, and at-least-once delivery plus a delivery-log idempotency check trades an occasional duplicate for never silently dropping a notification. A "hot event type" is explicitly distinguished from a "hot partition" as a different failure mode. Elevated from `study-packs/week-08/09-design-exercise-notification-system.md`. |
| [Distributed Job Scheduler](distributed-job-scheduler.md) | Executors and Thread Pool Sizing | A p50-vs-p99 job-duration spread (200ms vs. 30s) drives a two-pool worker architecture; lease-based claiming (not a distributed lock) self-heals on crash without a failure-detection mechanism. Elevated from `study-packs/week-09/09-design-exercise-distributed-job-scheduler.md`. |
| [Real-Time Chat System](real-time-chat-system.md) | Real-Time Delivery: WebSocket, SSE, and Long-Polling | A connection-routing problem, not a storage problem: a stateful WebSocket connection is pinned to one gateway node, so fan-out requires a separate, deliberately lossy connection registry (`userId -> gateway node`) kept structurally independent of the durable, persist-before-publish message store — a stale registry entry causes a routing delay, never message loss. New entry, not elevated from a study-pack exercise; see the file's own sourcing note. |
| [Ticket and Event Booking System](ticket-and-event-booking-system.md) | Optimistic vs. Pessimistic Locking | An inventory-contention problem under a thundering-herd flash-sale spike: a virtual waiting room sheds load before it reaches the seat-inventory system, and seat holds use optimistic compare-and-swap rather than a pessimistic lock held across a human-paced checkout flow. The waiting room fails closed (correct under overload); the inventory system never oversells (correct under any load) — two deliberately different failure-mode priorities in the same design. New entry, not elevated from a study-pack exercise; see the file's own sourcing note. |
| [URL Shortener System](url-shortener-system.md) | Caching Strategies and Invalidation | A caching problem, not a scaling-the-writes problem: an extreme (100:1+) read:write ratio on a critical-latency redirect path, made simple by a mapping that's immutable once created — there is no cache-invalidation problem to solve at all, since nothing an existing short link maps to ever legitimately changes. A pre-allocated key-block generator avoids write-path contention; click counting is deliberately asynchronous and off the redirect's own critical path. New entry, not elevated from a study-pack exercise; see the file's own sourcing note. |
| [Distributed Key-Value Store](distributed-key-value-store.md) | Data Partitioning and Consistent Hashing / CAP Theorem | Unlike every other entry, this problem *is* the storage primitive, not an application on top of one: consistency and availability are made explicit, tunable per-request parameters (`R`/`W` against replication factor `N`) rather than one system-wide default, with hinted handoff keeping writes available during a replica outage and background anti-entropy converging replicas afterward. A hot key is named explicitly as a different, unfixable-by-scaling problem from a hot node. New entry, not elevated from a study-pack exercise; see the file's own sourcing note. |
| [Distributed Cache](distributed-cache.md) | Data Partitioning and Consistent Hashing / Resilience Patterns | A sharded key-value cache where consistent hashing's measured ~9.2% (vs. ~92.5% naive) remap cost is what makes node scaling routine, and three distinct failure shapes (node failure, hot keys, stampede) each need their own specific mitigation rather than one generic fix. Elevated from `study-packs/week-10/10-design-exercise-distributed-cache.md`. |
| [Metrics/Monitoring System](metrics-monitoring-system.md) | Percentiles, Tail Latency, and Coordinated Omission | A monitoring system whose own write path (1M points/s) forces histogram sketches instead of raw samples, and whose alert-evaluation path must be architecturally isolated from dashboard queries — plus a cardinality explosion, distinguished explicitly as a different failure mode from raw volume with a different fix. Elevated from `study-packs/week-11/09-design-exercise-metrics-monitoring-system.md`. |
| [Deployment Infrastructure for a Payments Notification Service](deployment-infrastructure-for-a-payments-notification-service.md) | CI/CD Pipeline Design and Deployment Strategies / Cloud Cost and Scaling Economics | Not a system design — a deployment-strategy review: compute placement, resource/probe sizing, durable no-silent-drop messaging, autoscaling a 10x daily peak/trough shape, and canary-with-human-gate deployment, each traced back to one of the scenario's two explicit constraints (never silently drop, deployment risk-aversion) rather than a generic checklist. Elevated from `study-packs/week-15/09-design-exercise-deployment-infrastructure.md`. |
| [JVM Sizing and Diagnostics Playbook for a Real-Time Pricing Service](jvm-sizing-and-diagnostics-playbook-for-a-real-time-pricing-service.md) | JVM Flags and Container Ergonomics / G1 Remembered Sets and Write Barriers | A documented operational runbook, not an architecture: region sizing, container-CPU-aware GC expectations, a hot cache's G1 remembered-set cost and its partitioning fix, a concrete leak-diagnosis command sequence, and pre-warming both branches of a flag rollout to absorb deoptimization cost during controlled warmup. Elevated from `study-packs/week-16/09-design-exercise-jvm-sizing-and-diagnostics-playbook.md`. |
| [JVM Tuning Playbook for a Market-Data Service](jvm-tuning-playbook-for-a-market-data-service.md) | ZGC and Shenandoah / Native Memory, Direct Buffers, and Off-Heap | A sub-millisecond-p99 tuning playbook built entirely on measurement-before-fix: a `WeakHashMap` misused as a bounded cache, `-Xmx` not accounting for NIO direct-buffer memory, G1-vs-ZGC as a measured (not assumed) decision, escape analysis likely already eliminating a suspected allocation cost, and `-Xlog:safepoint` for a latency blip invisible to GC-log-only monitoring. Elevated from `study-packs/week-19/10-design-exercise-jvm-tuning-for-a-market-data-service.md`. |
| [Security Review of a Multi-Tenant Expense-Approval Platform](security-review-of-a-multi-tenant-expense-approval-platform.md) | OWASP Top 10 for Backend Services / Multi-Tenancy Isolation Models | A shared-schema (pool) multi-tenant platform reviewed across seven security dimensions: an IDOR-shaped access-control gap on fetch-by-ID, correct password hashing and enforced TLS, an approval rule RBAC structurally cannot express, parameterized search plus output encoding as separate required defenses, Row-Level Security with an explicit `BYPASSRLS`/superuser audit as tenant isolation's real backstop, proactive payments-key versioning and rotation, and SBOM scanning on a shared base image. Elevated from `study-packs/week-17/11-design-exercise-multi-tenant-expense-platform-security-review.md`. |
| [Test Strategy for a Checkout Service](test-strategy-for-a-checkout-service.md) | Mutation and Property-Based Testing / Contract Testing for Services | An 88%-coverage suite that missed a real boundary bug, used to reframe coverage as necessary-not-sufficient: mutation testing scoped to boundary-heavy modules plus a property-based sweep for the boundary class, consumer-driven contract testing (checkout as the contract owner) for an independently-evolving inventory service, percentile-threshold load testing and a failure-mode stress test for a new payment provider, and a narratable test-first live-coding round designed around specific, observable candidate signals. Elevated from `study-packs/week-18/09-design-exercise-test-strategy-for-a-checkout-service.md`. |

## How this relates to other deliverables

- `handbook/` — canonical explanations of individual concepts (storage selection, partitioning, isolation levels) that a full system design draws on; this Atlas references them rather than re-teaching them.
- `interview-playbook/system-design/` — the live-delivery discipline (time-boxing, handling mid-round changes) for running a design exercise like these under interview conditions.
- `cheat-sheets/` — one-page rapid review of a single canonical chapter's content, not a full worked system.
