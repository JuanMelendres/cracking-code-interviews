    1. Why This Matters¶

    "What's the difference between JVM, JDK, and JRE?" and "what are Java's primitive types?" are two of the single most commonly asked Java interview questions at the Junior level — and two of the most commonly answered from memorized definitions rather than real understanding. This chapter exists because a 2026-09-08 audit found this repository's own 02-java domain had no dedicated coverage of either: java-syntax-fundamentals-variables-control-flow-and-methods.md uses primitive types constantly (int, boolean, double) without ever listing all eight or explaining their real ranges, and nothing in this domain explained the JVM/JDK/JRE distinction at all. A candidate who can recite "JDK is a superset of JRE which is a superset of JVM" but can't explain what a javac-less JRE-only download actually was (or why Oracle stopped shipping one) gives a memorized, not understood, answer — and an interviewer who asks one clarifying question finds that out immediately.

    2. Prerequisites¶

    None — this is a true entry point. If you have never installed Java or run javac from a terminal, read this chapter before Java Syntax Fundamentals.

    3. Foundation (L1)¶

    The JVM (Java Virtual Machine) is a specification and its implementation: a program that executes Java bytecode (.class files) on a specific operating system and CPU architecture. It is the layer that makes "write once, run anywhere" real — the same compiled .class file runs unmodified on Windows, Linux, or macOS, because each platform has its own JVM implementation that knows how to translate the same bytecode into that platform's real machine instructions.

    The JDK (Java Development Kit) is everything you need to write and build Java software: a JVM, plus the compiler (javac), plus development tools (jar, javadoc, jdb, jshell, and others), plus the standard library's compiled classes. If you are writing Java code, you have a JDK installed — there is no way to compile a .java file into a .class file without one.

    The JRE (Java Runtime Environment), historically, was a smaller bundle: a JVM plus the standard library's compiled classes, but no compiler and no development tools — enough to run already-compiled Java programs, not to build them. Oracle stopped distributing a standalone JRE after Java 8/9 (see Section 12 for exactly why); every mainstream JDK download today includes everything a JRE used to provide, bundled together. The JRE-as-a-separate-thing distinction is now almost entirely historical — but it remains a very commonly asked interview question, so understanding what it used to mean, and why it changed, is worth more than reciting the old three-layer diagram as if it still described reality.

    Java has exactly eight primitive types — not classes, not objects, just raw values stored directly in memory:

    Type Size Range Default value
    byte 1 byte (8 bits) -128 to 127 0
    short 2 bytes (16 bits) -32,768 to 32,767 0
    int 4 bytes (32 bits) -2,147,483,648 to 2,147,483,647 0
    long 8 bytes (64 bits) ±9,223,372,036,854,775,807 0L
    float 4 bytes (32 bits) ~7 significant decimal digits 0.0f
    double 8 bytes (64 bits) ~15 significant decimal digits 0.0d
    char 2 bytes (16 bits) 0 to 65,535 (a UTF-16 code unit) ''
    boolean not specified by the JLS true or false false

    A primitive variable holds its value directly — no allocation, no object header, no garbage collection involvement for the variable itself. This is the storage model Java Syntax Fundamentals's own Section 5 already describes; this chapter's job is the exhaustive, ranges-included reference that chapter deliberately didn't spend space on.

    4. Core Concepts (L2)¶

    Every primitive type has a corresponding wrapper class — Integer for int, Double for double, Boolean for boolean, and so on — because Java's generic collections (List<Integer>, not List<int>) and anything requiring an object reference cannot hold a raw primitive. Autoboxing is the compiler automatically converting a primitive to its wrapper (Integer boxed = 5; really compiles to Integer boxed = Integer.valueOf(5);); auto-unboxing is the reverse (int i = boxed; compiles to int i = boxed.intValue();). Both happen silently, which is exactly why Section 8's mistakes are so easy to make without noticing.

    Integer caching is a real, specific JVM behavior worth knowing precisely: Integer.valueOf(int) caches and reuses Integer objects for values from -128 to 127 (the JLS guarantees this range as a minimum; some JVMs cache more). This means two autoboxed Integers with the same value in that range are the same object (== is true), while the same comparison outside that range produces two different objects (== is false) — a real, measured, and extremely common interview trap, demonstrated in Section 7.

    JVM vs. JDK vs. JRE, restated precisely for interview purposes: the JVM executes bytecode; the JDK is what you install to develop Java (JVM + compiler + tools); a standalone JRE (JVM + standard library, no compiler) is what you used to install if you only needed to run already-built Java software and never intended to write or compile any yourself. Since Java 11, Oracle and most other distributors ship only the JDK — there is no separate, smaller JRE-only download from the mainstream vendors anymore, though jlink (introduced with the Java Platform Module System, JEP 220) lets a developer build a custom, minimal runtime image containing only the modules an application actually needs — the modern, more precise replacement for "just ship the JRE."

    5. How It Works Internally (L3)¶

    A .java source file is compiled by javac into one or more .class files containing bytecode — a platform-independent instruction set, not the native machine code the CPU actually executes. When you run java SomeClass, the JVM loads that bytecode, verifies it (checking, among other things, that it doesn't attempt operations that would violate memory safety), and then executes it — either by interpreting each bytecode instruction one at a time, or, for code that runs often enough (a "hot" method or loop), by compiling it just-in-time (JIT) into real native machine code for the actual CPU the JVM is running on. This is why a Java program's performance profile is unusual compared to a purely compiled language: an interpreted hot path is slow initially, then gets progressively faster as the JIT compiler kicks in — an effect real JMH benchmarking has to deliberately warm up past, per Benchmarking & JMH Pitfalls.

    Primitive types are given this special, non-object treatment specifically for performance: an int[] of a million elements is a million contiguous 4-byte slots with zero object overhead, while an Integer[] of the same size is a million references, each pointing to a separately-allocated Integer object elsewhere on the heap (unless it happens to hit the -128..127 cache) — a real, measurable memory and cache-locality cost, which is exactly why performance-sensitive code reaches for primitive arrays over boxed collections.

    6. Practical Usage¶

    Use int as your default integer type unless you have a specific reason not to (a value that genuinely might exceed ~2.1 billion, in which case use long); use double as your default floating-point type unless you specifically need float's smaller memory footprint (e.g., huge arrays of approximate values) and can tolerate its lower precision. Never use float or double for money or anything requiring exact decimal arithmetic — use BigDecimal instead, precisely because of the real imprecision demonstrated in Section 7. Use wrapper classes only when you must (in a generic collection, or when a value genuinely needs to represent "no value" via null) — a primitive is always cheaper when a null state isn't meaningful.

    7. Examples¶

    Every claim below is verified against a real, compiled, executed program at practice/java/oop-fundamentals/platform-basics/, run on OpenJDK 21.0.12 — 11/11 assertions pass, full transcript in that directory's primitive-types-output.txt.

    // The real, measured Integer cache gotcha.
Integer cachedA = 127;
Integer cachedB = 127;
Integer notCachedA = 128;
Integer notCachedB = 128;

System.out.println(cachedA == cachedB);       // true  — both from the cache, same object
System.out.println(notCachedA == notCachedB); // false — both new objects, outside the cache range
System.out.println(notCachedA.equals(notCachedB)); // true — equals() correctly compares VALUE

    // The real 0.1 + 0.2 floating-point surprise.
double sum = 0.1 + 0.2;
System.out.println(sum); // 0.30000000000000004, not exactly 0.3

    // A real NullPointerException from auto-unboxing a null wrapper — not a silent 0.
Integer maybeNull = null;
int crashes = maybeNull; // throws NullPointerException here, at the auto-unboxing call

    The real JDK tooling evidence — confirming a JDK genuinely bundles the compiler and development tools, not just the runtime — is captured in that same directory's jdk-tooling-transcript.txt: a real javac -version output, and a real listing of this machine's JDK bin/ directory showing javac, jar, javadoc, jlink, jshell, and more, plus 69 real .jmod files available for jlink to build a custom runtime from.

    8. Common Mistakes¶

    • Comparing boxed wrapper values with == instead of .equals() — works accidentally for small cached values (-128..127), then silently breaks the first time the value exceeds that range in production. This is the single most common real bug this chapter's Integer-cache demo exists to prevent.
    • Using float/double for money — 0.1 + 0.2 != 0.3 is not a rounding curiosity, it is why every real financial system uses BigDecimal or integer minor-units (cents) instead.
    • Assuming a null wrapper unboxes to 0 or false — it throws a real NullPointerException instead, at the exact line the unboxing happens, which can look confusingly unrelated to the actual null value's origin.
    • Reciting the JDK/JRE/JVM hierarchy as if a standalone JRE still exists — an interviewer who asks "so if I wanted to just run Java without developing, what would I download today?" is testing whether you understand this is now mostly historical, not whether you memorized the old diagram.

    9. Edge Cases¶

    • char is unsigned (0 to 65,535) — the only primitive integer type in Java without a negative range, because it represents a UTF-16 code unit, not a signed number.
    • boolean's in-memory size is deliberately unspecified by the Java Language Specification — different JVMs are free to represent it as 1 byte, 4 bytes, or however else is convenient for that implementation, since a program can never observe its actual storage size.
    • Integer caching applies to autoboxing via Integer.valueOf(int) specifically — new Integer(127) (deprecated since Java 9, for exactly this kind of confusion) always allocates a new object and is never cache-eligible.

    10. Performance Implications¶

    A primitive array has zero per-element object overhead; a boxed wrapper array pays for both a reference (4 or 8 bytes, depending on JVM pointer compression) and a separately-heap-allocated object (typically 16 bytes of header plus the actual value) per element, unless the value happens to be a cached small integer. For large numeric datasets, this is a real, measurable difference in both memory footprint and cache locality — one of the concrete reasons Collections Usage Fundamentals eventually revisits primitive-vs-boxed trade-offs once collection performance actually matters.

    11. Trade-offs¶

    Choice When it helps When it hurts
    Primitive (int) Performance-critical code, large arrays, no need for null Can't go in a generic collection directly, no null state
    Wrapper (Integer) Generic collections, need for a null/"absent" state Extra memory, extra indirection, == pitfall
    float Memory-constrained huge arrays of approximate values Lower precision, wrong choice for money
    double The correct default for floating-point math Twice float's memory cost

    12. Senior-Level Considerations (L3)¶

    A Senior engineer should be able to explain why Oracle stopped shipping a standalone JRE: the Java Platform Module System (JPMS, introduced in Java 9, JEP 220) restructured the JDK itself into modules, which made it possible for jlink to assemble a custom runtime image containing exactly the modules an application needs — a strictly better solution than a one-size-fits-all JRE bundle, since it can be smaller than the old JRE ever was while still including whatever a specific application actually requires. This is also why container images for Java applications shrank significantly once teams adopted jlink-based custom runtimes instead of bundling a full JDK into a production image — directly relevant to Docker and Containers Fundamentals's own image-size discussion.

    13. Staff/System-Level Considerations (L4)¶

    At Staff scope, the JDK/JRE/JVM distinction becomes an organizational packaging decision: should the company standardize on full-JDK production images for debuggability (a stack trace tool, jcmd, jstack all available in production if needed), or minimal jlink-built runtime images for smaller attack surface and faster cold-start in a container-orchestrated environment? Neither answer is universally correct — it is a real trade-off between operability and image size/security surface, decided per organization's actual incident-response needs, not by default.

    15. Interview Questions¶

    Question 1: What's the difference between JVM, JDK, and JRE?¶

    Expected answer: JVM executes bytecode; JDK = JVM + compiler + dev tools (what you install to write Java); JRE (historically) = JVM + standard library only, no compiler (what you installed to only run Java). Oracle stopped distributing a standalone JRE after Java 8/9; every modern JDK download includes everything a JRE used to provide.

    Common mistakes: reciting only "JDK contains JRE, JRE contains JVM" without being able to say what a JRE actually lacked (the compiler), or not knowing that standalone JREs are effectively a historical artifact now.

    Follow-up questions: "If there's no separate JRE download anymore, how would you ship a smaller runtime for a container?" (Expected: jlink, JPMS modules.)

    Senior-level expectations: connects this to jlink/JPMS and container image size.

    Staff-level expectations: frames it as an organizational operability-vs-image-size trade-off, not a single correct answer.

    Question 2: What are Java's primitive types, and why does Integer a = 127; Integer b = 127; a == b return true while the same code with 128 returns false?¶

    Expected answer: the eight primitives (byte/short/int/long/float/double/char/boolean); Integer.valueOf caches boxed values from -128 to 127, so two boxed 127s are the same cached object, while two boxed 128s are separate objects — == compares object identity, not value, for wrapper types.

    Minimum acceptable answer: knows to use .equals() for wrapper value comparison, even without the exact cache-range number.

    Strong Senior answer: explains the mechanism (which method causes caching — autoboxing via valueOf, not new Integer()) and can state that this is a real, common production bug shape.

    Staff-level extension: connects it to a broader principle — comparing any wrapper/boxed type by reference instead of value is a class of bug, not a one-off Integer quirk (the same applies to Long, Short, Character in Java's specification, all of which cache small values too).

    Common mistakes: guessing the cache boundary is exactly Integer.MAX_VALUE/MIN_VALUE, or claiming all Integer comparisons with == are unsafe (small, commonly-used constants are actually safe — the bug is relying on that accidentally).

    Likely follow-ups: "does this same caching happen for Long? For Boolean?" (Yes for both, per the JLS.)

    Evaluation criteria: correctly names the mechanism (autoboxing cache), correctly states the fix (.equals()), and doesn't overstate or understate the scope of the gotcha.
